## Live Facts

### Booking and payment shape

The live `public.bookings` table has no payment-attempt or confirmation relation. Its payment-relevant columns are:

- Identity and ownership: `id uuid` primary key with `gen_random_uuid()`, `mua_id uuid NOT NULL`, nullable `invite_id uuid`, and nullable `package_id bigint`.
- Client and appointment facts: nullable `client_name`, `client_phone`, and `venue_address`; non-null `event_date date` and `event_time time`; nullable `venue_lat` and `venue_lng`.
- Current monetary values: `total_amount`, `deposit_amount`, and `balance_amount`, all `numeric(10,2) NOT NULL`. There is no `currency`, line-item, travel-fee, surcharge, payment-kind, or amount-verified column.
- Current proof locations: nullable `receipt_url` and nullable `balance_receipt_url`, each a single mutable `text` slot.
- Booking state and operational tokens: non-null `status booking_status` defaulting to `CHECKING_OUT`; nullable unique `approval_token` and `calendar_uid`; non-null `locked_at`, `created_at`, and `updated_at` timestamps.
- Balance-link fields: nullable `balance_due_date`, nullable unique `balance_token` defaulting to `gen_random_uuid()`, and nullable `last_overdue_notified_at`.

Supporting commercial inputs remain in mutable source tables: `packages.price`; invite `transport_fee_override`, `custom_surcharge`, `deposit_mode_override`, and `deposit_value_override`; and MUA config `deposit_mode` and `deposit_value`. None is copied into a payment-specific immutable snapshot by the current schema.

The live `booking_status` enum is:

`CHECKING_OUT`, `PENDING_APPROVAL`, `CONFIRMED`, `REJECTED`, `FULLY_PAID`, `EXPIRED`, `CANCELLED`, `COMPLETED`.

`REJECTED` exists in the enum, but the current MUA UI rejects a deposit by setting the booking to `CANCELLED`, not `REJECTED`. No enum value identifies a verified Deposit or verified Balance event.

### Current RPC behavior

The relevant live functions are callable by `anon`, `authenticated`, and `public` according to `has_function_privilege`. The function definitions and security modes are in the fresh snapshot at `docs/agents/supabase-state.md` lines 213-316 and 544-735.

| Function | Live behavior relevant to confirmation generation |
|---|---|
| `secure_checkout_slot` | Not `SECURITY DEFINER`. It locks the MUA config, validates the Booking Link, blackout date, package, capacity, working hours, and overlap, then inserts `CHECKING_OUT`. It accepts `p_total_amount`, `p_deposit_amount`, and `p_balance_amount` from the caller rather than calculating them from package/config/invite facts. |
| `finalize_receipt_submission` | `SECURITY DEFINER`. It changes the selected `CHECKING_OUT` booking to `PENDING_APPROVAL` and stores the supplied `p_receipt_url`; it then marks the separately supplied `p_invite_id` used. It does not check that the invite belongs to the booking, does not recheck the ten-minute `locked_at` window, and returns booking/package/config notification data. |
| `finalize_balance_payment` | `SECURITY DEFINER`. It locks a booking only when its status is `CONFIRMED`, then changes it to `FULLY_PAID` and stores the supplied `p_receipt_url` in `balance_receipt_url`. It does not receive or validate `balance_token`, `balance_due_date`, payment amount, or a MUA confirmation action. |
| `cleanup_stale_bookings` | `SECURITY DEFINER`. It expires stale `CHECKING_OUT` rows after ten minutes, cancels past-event `PENDING_APPROVAL` rows, and completes past-event `CONFIRMED` rows. It does not create payment confirmations. |

The current deposit route uploads a proof image first, obtains a public URL, and calls `finalize_receipt_submission`. The current balance route does the same and calls `finalize_balance_payment`; therefore Balance proof upload currently advances `CONFIRMED -> FULLY_PAID` without an explicit MUA verification step. The MUA dashboard directly updates `PENDING_APPROVAL -> CONFIRMED` (and calculates the balance due date/token client-side).

### RLS and data access

RLS is enabled (not forced) on all seven relevant public tables and on `storage.buckets` and `storage.objects` in the live instance.

Relevant public-schema policies are:

- `bookings`: MUAs have `ALL` access when `auth.uid() = mua_id`; anonymous clients can `SELECT` a `CONFIRMED` row when `balance_token IS NOT NULL`; anonymous clients can also `SELECT` a booking whose `invite_id` points to an unused, unexpired invite.
- `invites`: public `SELECT` is currently allowed by a policy whose `USING` expression is `true`; MUAs have `ALL` access to their own invites.
- `mua_configs`, `muas`, and `packages`: public baseline `SELECT` policies exist; MUA management policies are scoped by `auth.uid()` where applicable.
- There is no direct anonymous booking `INSERT`, `UPDATE`, or `DELETE` policy. The public checkout/finalization path therefore depends on the RPC security mode and its SQL behavior rather than ordinary table writes. In particular, the live `secure_checkout_slot` is not security-definer while `bookings` has no anonymous insert policy; this combination must be explicitly tested or corrected as part of any future implementation work.

The full current public policy list is in `docs/agents/supabase-state.md` lines 737-757.

### Storage visibility and policies

Live bucket metadata:

| Bucket | Public | Type | File-size limit | Allowed MIME types |
|---|---:|---|---|---|
| `qr-codes` | true | STANDARD | none configured | none configured |
| `receipt-uploads` | true | STANDARD | none configured | none configured |

Supplemental live `storage.objects` policies are:

- `Allow public clients to upload receipts`: `public`, `INSERT`, only checks `bucket_id = 'receipt-uploads'`.
- `Allow public read access on receipt-uploads`: `public`, `SELECT`, only checks `bucket_id = 'receipt-uploads'`.
- QR policies permit public reads and authenticated MUA writes under an MUA-owned folder.
- There is no receipt-object update/delete policy for public clients and no path-to-booking, MIME, size, or uploader binding in the receipt policies.

The current application uses `getPublicUrl` for both deposit and Balance proof images. Consequently, existing proof URLs are public bearer URLs, not protected confirmation access. No Storage object retention or lifecycle policy was identified in the live checks.

### Indexes and constraints

Relevant live indexes include:

- `bookings_pkey`, unique nullable `bookings_approval_token_key`, `bookings_balance_token_key`, and `bookings_calendar_uid_key`.
- `idx_bookings_balance_token`, `idx_bookings_invite_id`, `idx_bookings_locked_at` (partial for `CHECKING_OUT`), `idx_bookings_mua_date`, `idx_bookings_mua_date_status` (partial for `CONFIRMED`, `PENDING_APPROVAL`, and `CHECKING_OUT`), `idx_bookings_overdue_reminder` (partial for `CONFIRMED` with positive balance), and `idx_bookings_status`.
- Unique `invites_token_key` plus `idx_invites_token`, and `idx_invites_mua_expires`.

There is no index for confirmation number, payment kind/history, confirmation token hash, or confirmation-to-booking lookup beyond the booking primary key and invite index. The active-booking partial index also excludes `FULLY_PAID`, although the public availability queries include `FULLY_PAID`; the general `(mua_id, event_date)` index remains available.

The live constraints also confirm `bookings.invite_id` is `ON DELETE SET NULL`, `bookings.package_id` is `ON DELETE SET NULL`, and `bookings.mua_id` is `ON DELETE CASCADE`. Thus a future confirmation cannot safely rely on a live package or invite row remaining available.

### Migration and deployment constraints

- The live `public.schema_migrations` table contains only version `20260526065747`.
- The current repository has no tracked `db/migrations` or `supabase/migrations` directory. It retains only three SQL files under `supabase/rpc/`; the generated snapshot is explicitly a live-cloud capture, not a migration source.
- Git history shows the earlier migration/schema files were removed in commit `62cfe3d` when the Supabase snapshot workflow was introduced. The historical migration chain added the expired status, balance fields/policies, and performance indexes, but those files are not a current deployment mechanism.
- `package.json` exposes `npm run sync:supabase` but no database migration/apply command. `wrangler.jsonc` and `.github/workflows/cron.yml` deploy/run the Cloudflare application and cron endpoints; they do not deploy database schema or Storage policy changes.

Any new confirmation tables, columns, indexes, RPCs, RLS rules, or Storage privacy changes therefore need a separately chosen database deployment mechanism and a post-deployment live recapture. This research does not create one.

## Inferences and Constraints

- The current booking row is a mutable operational record, not an immutable payment event. The two proof URL columns can hold at most the latest Deposit and Balance proof and cannot preserve rejection, correction, duplicate, or replacement history.
- `PENDING_APPROVAL` means proof submitted in the current flow, while `FULLY_PAID` can mean only that the Balance upload RPC ran. Neither status is sufficient as the identity of a MUA Payment Confirmation.
- Recomputing a historical confirmation from current package/config/invite rows would be unsafe: the checkout RPC accepted caller-supplied amounts, commercial inputs are mutable, and package/invite references can be nulled by deletion.
- The public receipt bucket and public `getPublicUrl` usage are incompatible with a protected confirmation artifact unless the target explicitly treats old proof URLs as a legacy privacy issue. A new confirmation link must not inherit public receipt-image access merely because the existing proof upload succeeds.
- UUID booking/balance/invite tokens provide lookup or bearer access, but the live schema provides no confirmation-specific secret, expiry, revocation, or immutable version model. Those properties must be specified rather than inferred from existing tokens.

## Implications for Downstream Decisions

### 01 - Confirmed payment event model

Define Deposit and Balance confirmation as explicit MUA actions/events separate from proof upload. The implementation must not use the current Balance upload RPC as the confirmation boundary. The decision must also state how booking status changes relate to a payment event, how rejected proofs remain non-confirmed, and how legacy `CONFIRMED`/`FULLY_PAID` rows are treated. The event write and any booking transition should be atomic and server-authorized because current direct MUA updates and public RPCs do not encode a complete state machine.

### 02 - Authoritative pricing snapshot

The confirmation cannot treat hidden checkout amounts as authoritative: `secure_checkout_slot` persists caller-provided totals, Deposit, and Balance values, while no currency or line-item breakdown is stored. Decide which server-authoritative facts are frozen at booking/verification time, how invite overrides are captured, and whether legacy bookings are eligible for confirmation. Do not depend on current package/config/invite rows for an old booking without an explicit backfill or uncertainty rule.

### 03 - Confirmation numbering and versioning

There is no confirmation table, sequence, human-facing number, payment-kind discriminator, or immutable replacement link. The single proof URL fields cannot implement history. Decide the durable record and uniqueness scope for separate Deposit and Balance confirmations, replacement/supersession rules, and the legacy policy. The implementation will need new uniqueness and lookup indexes rather than reusing `balance_token`, `approval_token`, or `calendar_uid` as a confirmation number.

### 06 - Protected confirmation access

Do not expose a generated confirmation or proof image through `receipt-uploads` public URLs. Decide whether confirmations are rendered through an authorization-checked route, stored in private Storage, or both; define a separate client secret/link from the Booking Link Token and Balance Token; and specify expiry, revocation, correction behavior, and retention. Authenticated MUA access can use the MUA-owned booking boundary, but anonymous Client access must not rely on the current broad public Storage `SELECT` policy or on a UUID being hard to guess.
